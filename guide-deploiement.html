Mettre un site en ligne à chaque git push

Tu modifies ton projet sur ton PC, tu fais un commit et un push, et les fichiers modifiés partent tout seuls sur ton hébergement, comme sur Vercel ou Netlify. Ce guide reprend tout ce qu'on a mis en place, les erreurs rencontrées et comment les éviter.

Valeurs de ton installation : compte GitHub nadhiroff, serveur FTP srv200.arobase360.com, port 21, protocole ftp. Les commandes en noir se copient avec le bouton Copier. Les cadres en pointillés montrent ce que tu dois voir à l'écran.

Le kit est sur GitHubnadhiroff/kit-deploiement_ftp-github
Télécharger le kit (.zip) Voir le dépôt

Le principe

Ton PCtu codes, puis git push
→
GitHubreçoit le code du projet
→
GitHub Actionstrie et compare les fichiers
→
Ton hébergeurreçoit seulement ce qui a changé

Trois pièces travaillent ensemble :

  • Le dépôt central nadhiroff/deploy-workflows sur GitHub. Il contient le moteur de déploiement (deploy.yml). Il existe une seule fois, pour tous tes projets.
  • La commande deploy-init sur ton PC. Tu la lances une fois dans chaque projet pour le brancher au moteur.
  • Dans chaque projet, deux petits fichiers créés par deploy-init : .github/workflows/deploy.yml (10 lignes qui appellent le moteur) et .deployignore (la liste de ce qui ne doit pas aller en ligne).

Les identifiants FTP ne sont dans aucun fichier. Ils sont rangés, chiffrés, dans les secrets GitHub de chaque projet.

Ce qui part en ligne, et ce qui ne part pas

Quatre filtres s'appliquent dans cet ordre :

  1. Seuls les fichiers commités et poussés dans Git. Un fichier dans .gitignore ne part jamais.
  2. Seulement le dossier choisi (par défaut tout le projet, noté .).
  3. Moins ce qui est listé dans .deployignore.
  4. Moins les exclusions de sécurité, toujours actives : .git, .github, .env, .env.*, node_modules, .deployignore.

À chaque déploiement, le moteur compare avec le déploiement précédent. Il envoie les fichiers nouveaux ou modifiés et supprime du serveur les fichiers supprimés de Git. Un fichier exclu par .deployignore n'est jamais ni envoyé, ni modifié, ni supprimé.

2. Le dépôt central une seule fois en tout

Le moteur vit sur GitHub. Il n'est pas lié à un PC. Commence par vérifier s'il existe déjà :

gh repo view nadhiroff/deploy-workflows --json name -q .name 2>/dev/null && echo "✅ existe déjà" || echo "➜ à créer"
  • « existe déjà » : rien à créer. Passe directement à l'étape d'accès pour vérifier le réglage.
  • « à créer » : suis les étapes ci-dessous.

Créer le dépôt central

mkdir -p ~/deploy-workflows/.github/workflows
cp ~/Téléchargements/kit-deploiement/deploy.yml ~/deploy-workflows/.github/workflows/deploy.yml
cd ~/deploy-workflows
git init -b main
git add .
git commit -m "workflow de déploiement réutilisable"
gh repo create deploy-workflows --private --source=. --push
cd ~

Autoriser tes projets à l'utiliser

Sans ce réglage, chaque déploiement échoue avec workflow was not found. C'est l'erreur qu'on a eue sur summary.

gh api -X PUT repos/nadhiroff/deploy-workflows/actions/permissions/access -f access_level=user
gh api repos/nadhiroff/deploy-workflows/actions/permissions/access
Résultat attendu
{
  "access_level": "user"
}

Équivalent dans le navigateur : dépôt deploy-workflows → Settings → Actions → General → section Access → Accessible from repositories owned by the user → Save.

Règle de visibilité

Le dépôt central est privé. GitHub interdit à un projet public d'utiliser un moteur privé. Tous tes projets branchés doivent donc être privés, ce qui protège aussi ton code et tes fichiers.

Mettre le moteur à jour plus tard

Si on améliore deploy.yml, tu le remplaces une fois ici et tous tes projets en profitent. Ce bloc prend le deploy*.yml le plus récent de tes Téléchargements. Il ne copie que si le fichier contient bien la dernière correction, ce qui évite le piège du fichier ancien qu'on a rencontré.

[ -d ~/deploy-workflows ] || gh repo clone nadhiroff/deploy-workflows ~/deploy-workflows
NOUVEAU="$(ls -t ~/Téléchargements/deploy*.yml ~/Téléchargements/kit-deploiement/deploy.yml 2>/dev/null | head -1)"
echo "Fichier utilisé : $NOUVEAU"
if grep -q delete-candidates "$NOUVEAU"; then
  cp "$NOUVEAU" ~/deploy-workflows/.github/workflows/deploy.yml
  cd ~/deploy-workflows && git pull -q && git add . && git commit -m "mise à jour du moteur de déploiement" && git push
  cd ~
else
  echo "❌ Ce fichier est une ancienne version"
fi

Vérifier la version qui est vraiment sur GitHub :

gh api repos/nadhiroff/deploy-workflows/contents/.github/workflows/deploy.yml --jq .content | base64 -d | grep -c delete-candidates
Résultat attendu
4

Un nombre supérieur à 0 signifie que c'est la bonne version. Un 0 signifie que c'est une ancienne version.

C. Projet déjà en ligne GitHub + PC + serveur

Exemple réel : calculateur_performance, développé dans /var/www/html/calculateur_performance_a_envoyer/calculateur_performance, dépôt nadhiroff/calculateur_performance, en ligne dans /calculateur_performance/.

.deployignore ou .gitignore ?

.deployignore : le fichier reste sur GitHub mais ne va pas en ligne. C'est le cas pour la documentation, les tests et les fichiers de travail.

.gitignore : le fichier ne va nulle part, ni sur GitHub ni en ligne. C'est le cas pour les mots de passe, .env et les données personnelles de clients. Si un tel fichier est déjà commité, retire-le de Git sans l'effacer de ton PC :

echo "/BISON.xlsx" >> .gitignore
git rm --cached BISON.xlsx
git commit -m "retrait d'un fichier privé du dépôt"
git push

Le fichier reste dans l'historique Git. C'est sans gravité si le dépôt est privé.

Sur le serveur et dans le navigateur

FileZilla → F5 : les fichiers modifiés ont l'heure du déploiement. Ouvre le site et recharge avec Ctrl+Maj+R pour ignorer le cache.

Protéger le fichier .deploy-state

Le moteur dépose dans chaque dossier distant un fichier .deploy-state, qui contient la liste de tes fichiers. Pour qu'il ne soit pas lisible depuis le navigateur, ajoute ceci au .htaccess du projet, puis commite et pousse :

<Files ".deploy-state">
  Require all denied
</Files>

Ne supprime pas .deploy-state du serveur. Sans lui, le déploiement suivant renvoie tous les fichiers. Ce n'est pas grave, juste plus long.

Identifiants FTP et réglages

Ils sont dans les secrets du projet : sur GitHub, ouvre le projet → Settings → Secrets and variables → Actions. On ne peut plus lire leur valeur, seulement la remplacer.

SecretContenuExemple
FTP_SERVERHôtesrv200.arobase360.com
FTP_USERNAMEIdentifiantton identifiant FTP
FTP_PASSWORDMot de passejamais écrit nulle part
FTP_SERVER_DIRDossier distant/calculateur_performance/

Toutes ces commandes se lancent dans le dossier du projet :

gh secret list
gh secret set FTP_PASSWORD

La commande te demande la nouvelle valeur ; colle-la puis Entrée.

gh secret set FTP_SERVER_DIR --body "/nom_du_projet/"

Changer la branche, le protocole ou le dossier source

Ces réglages sont dans .github/workflows/deploy.yml du projet :

name: Déploiement

on:
  push:
    branches: ["main"]        # branche qui met en ligne
  workflow_dispatch:

jobs:
  deploy:
    uses: nadhiroff/deploy-workflows/.github/workflows/deploy.yml@main
    with:
      protocol: ftp           # ftp, ftps ou sftp
      port: 21
      source-dir: "."         # "." = tout le projet, ou "api" par exemple
      php-lint: true          # bloque si erreur de syntaxe PHP
    secrets: inherit

Modifie avec nano .github/workflows/deploy.yml, puis commite et pousse. Tu peux aussi relancer deploy-init : il demande confirmation avant d'écraser le workflow, redemande les identifiants, et garde ton .deployignore s'il existe.

Changer de PC

Rien n'est perdu : le moteur et tous tes projets sont sur GitHub, et les identifiants FTP sont dans les secrets GitHub.

  1. Refais la partie Installer sur un PC avec le kit récupéré sur GitHub.
  2. Le dépôt central existe déjà : vérifie seulement l'accès.
  3. Récupère chaque projet :
gh repo list nadhiroff --limit 50
mkdir -p ~/projets && gh repo clone nadhiroff/calculateur_performance ~/projets/calculateur_performance

C'est tout. Les projets déjà branchés n'ont pas besoin de deploy-init : leur workflow et leurs secrets sont sur GitHub. Le prochain git push déploie normalement.

Les fichiers que tu as mis dans .gitignore (.env, configuration locale) ne sont pas sur GitHub. Recrée-les à la main sur le nouveau PC.

Problèmes rencontrés et solutions

Tous ces cas sont arrivés pendant la mise en place.

workflow was not found … access-to-reusable-workflows

Cause : le projet n'a pas le droit d'utiliser le moteur central, soit parce que le réglage d'accès manque, soit parce que le projet est public.

Solution : refais l'étape d'accès et passe le projet en privé avec gh repo edit nadhiroff/PROJET --visibility private. Relance ensuite avec gh workflow run deploy.yml.

unknown flag: --accept-visibility-change-consequences

Cause : ta version de gh est plus ancienne et ne connaît pas cette option.

Solution : lance la commande sans elle : gh repo edit nadhiroff/PROJET --visibility private.

fatal: ni ceci ni aucun de ses répertoires parents n'est un dépôt git

Cause : tu es dans le mauvais dossier, souvent le dossier parent du projet.

Solution : va dans le dossier qui contient .git (vérifie avec ls -a). Pour le calculateur : cd /var/www/html/calculateur_performance_a_envoyer/calculateur_performance.

rien à valider, la copie de travail est propre (en mettant à jour le moteur)

Cause : le fichier copié était l'ancienne version. Le nouveau n'avait pas été téléchargé, ou il portait un autre nom, comme deploy(1).yml.

Solution : utilise le bloc de mise à jour du moteur, qui vérifie la version avant de copier.

cp: impossible d'évaluer '…/NOM_DU_FICHIER.yml'

Cause : un nom d'exemple a été copié tel quel au lieu du vrai nom de fichier.

Solution : regarde le vrai nom avec ls -lt ~/Téléchargements/deploy*.

Je ne trouve pas .deployignore

Cause : les fichiers qui commencent par un point sont cachés.

Solution : ls -a dans le terminal, Ctrl+H dans le gestionnaire de fichiers, ou ouvre-le directement avec nano .deployignore.

Le déploiement réussit mais le site n'apparaît pas dans FileZilla

Cause 1 : le dossier distant était /public_html/, alors que sur ton hébergement la racine est /. Les fichiers sont partis dans un dossier public_html qui n'est pas servi.
Solution : gh secret set FTP_SERVER_DIR --body "/nom_du_projet/" puis gh workflow run deploy.yml.

Cause 2 : les fichiers du site n'avaient jamais été commités. Seuls les fichiers de configuration étaient dans Git.
Solution : git add ., git commit, git push.

Cause 3 : FileZilla n'est pas actualisé. Appuie sur F5.

Le site ne se connecte plus à la base après le premier déploiement

Cause : le fichier de configuration local (par exemple config/config.php) était dans Git et a remplacé celui du serveur.

Solution : remets le fichier depuis ta sauvegarde, ou corrige-le dans FileZilla (clic droit → Afficher/Éditer). Ajoute ensuite /config/ dans .deployignore : il ne sera plus jamais touché, pas même supprimé.

Des fichiers privés sont partis en ligne (factures, Excel, tests)

Solution : ajoute-les dans .deployignore, commite, pousse, puis supprime-les à la main dans FileZilla. Le moteur ne supprime jamais un fichier exclu.

Un dépôt était public avec des fichiers privés dedans

Solution : gh repo edit nadhiroff/PROJET --visibility private immédiatement, puis vérifie avec gh repo view nadhiroff/PROJET --json visibility. Si les fichiers sont sensibles, considère qu'ils ont pu être copiés pendant qu'ils étaient publics.

.deployignore a perdu mes lignes

Cause : le projet a été réinitialisé (suppression de .git puis nouveau deploy-init), et un .deployignore neuf a été créé.

Solution : rajoute les lignes, commite, puis vérifie avec deploy-init --apercu.

found no in progress runs to watch

Cause : le déploiement n'a pas encore démarré, ou il a échoué tout de suite.

Solution : attends 5 secondes et relance gh run watch. Sinon, regarde gh run list : un X en 0 s signifie le plus souvent un problème d'accès au moteur (voir le premier problème).

Erreur SSL / TLS pendant l'envoi

Cause : l'hébergeur ne gère pas FTPS.

Solution : dans .github/workflows/deploy.yml, remplace protocol: ftps par protocol: ftp, puis commite et pousse.

Login incorrect / 530

Solution : l'identifiant ou le mot de passe est faux. Teste-les dans FileZilla, puis remplace-les avec gh secret set FTP_USERNAME et gh secret set FTP_PASSWORD.

Vérifier la syntaxe PHP en rouge

Cause : un fichier PHP contient une erreur. C'est voulu : rien n'est envoyé, le site en ligne reste intact.

Solution : gh run view --log-failed affiche le fichier et la ligne. Corrige, commite, pousse.

Avertissements jaunes « Node.js 20 is deprecated » ou « Ubuntu 26 »

Ce sont des informations de GitHub, pas des erreurs. Le déploiement fonctionne.

Un menu apparaît après gh run view et je suis bloqué

Choisis une ligne avec les flèches et Entrée, ou quitte avec Ctrl+C.
